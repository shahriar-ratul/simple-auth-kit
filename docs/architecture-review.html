easy-auth — Architecture Review

Grounded in direct source reads · registry/core, registry/combos/nestjs-prisma, cli/lib · updated 2026-08-23 · no-CI constraint applied
Layering Strengths Risks Recommendations Local Enforcement Priority
Verdict: sound, ship the fixes below Update: no CI — enforcement moved local

The hard decisions are correct. The gaps are all in enforcement, not design.

Deps-injection over interface abstraction, no-authz-in-JWT, fail-closed route tiers, version-key cache invalidation, and session-family revocation on refresh reuse are all textbook-correct and consistently applied. Nothing here is architecturally wrong. What's missing is the mechanical backstop that keeps good design good under scale and time: nothing automatically runs the one test suite that actually proves correctness, one of two in-memory stores doesn't get the same swap contract as its sibling, and a few comments describe a backend that was refactored out from under them. CI is explicitly off the table by decision — the enforcement recommendation below was revised to a local git hook, and every file count on this page was re-verified against the actual repo, not estimated.

2What's right (verified against source)

Deps-injection over interface abstraction

registry/core/session-policy.ts · registry/core/rbac.ts 
export function resolvePermissions(rolePermissionKeys: string[], directPermissionKeys: string[]): string[] {
  return [...new Set([...rolePermissionKeys, ...directPermissionKeys])].sort();
}
Why it matters: a single unified AuthStore interface is what plan/brief.md's decision 1 explicitly rejects as "the leaky lowest-common-denominator abstraction that made Lucia unmaintainable." Small purpose-scoped *Deps objects mean core has zero coupling to any combo and is testable with plain fakes — 56 unit tests with no framework bootstrapping.

The boot-time route-tier check is non-vacuous

registry/combos/nestjs-prisma/test/prove-cycle.ts:74-90 
// Adds a route to a real controller that declares no tier marker, exactly as writing
// `@Get("__tier-proof") untieredProofRoute() {}` in the source would.
// This is what makes the "fails at startup" assertion non-vacuous: asserting that a
// checker function throws when handed a synthetic class would prove only that the
// function works; this proves the running application refuses to start.
function addUntieredRoute(): () => void { ... }
Why it matters: most "we test our guardrails" claims mock the guardrail. This mutates the real controller prototype and boots the real app — the harder, more honest test to write, and the one actually run.

Permission cache: version-key invalidation, not TTL

registry/combos/nestjs-prisma/shared/src/permission-cache.ts 
// 1. Version-key invalidation, never eviction: a cache key embeds two generation
//    counters, and bumping one makes every key built from the old value unreachable.
// 2. Two counters: a subject counter per principal, a global policy counter.
//    A single global counter would flush everyone on any one user's grant change.
// 3. Negative results aren't cached — "not a member" is re-read every time.
Why it matters: the system's core promise is "a revocation lands on the caller's next request, not their next token." TTL-based caching breaks that promise for up to the TTL window; version-key invalidation doesn't. stats isn't decoration either — prove-cycle asserts N identical requests cause exactly one DB resolution.

Workspace isolation has no existence oracle

registry/combos/nestjs-prisma/variants/workspaces/src/authz.guard.ts:32-34 
// Same answer for "no such workspace" and "not your workspace" — a caller outside
// a workspace must not be able to probe whether it exists.
if (!authz) throw new ForbiddenException("not a member of this workspace");
Why it matters: this is the detail most multi-tenant implementations get wrong under time pressure — a 404 vs 403 split leaks workspace IDs to enumeration. It's collapsed to one error deliberately, cache-keyed on [userId, workspaceId] so membership changes are effective immediately.

No authorization in the JWT, applied consistently

registry/core/token-service.ts

Access-token signing omits roles/permissions keys entirely when the caller passes neither — not empty arrays, absent. Every downstream guard resolves from the database. The cost (a read on every authorized request) is paid deliberately and mitigated by the cache above, not hidden.

3What's wrong (also verified)

Rate limiter doesn't get the cache's swap contract — and it's worse than it looksrefined

registry/combos/nestjs-prisma/{shared/src/rate-limit.store.ts, variants/{base,workspaces}/src/auth.service.ts} 
// rate-limit.store.ts — bare class, no DI symbol:
export class InMemoryRateLimitStore implements RateLimitDeps { ... }

// auth.service.ts — injects the CONCRETE CLASS directly, confirmed in base AND workspaces:
@Inject(InMemoryRateLimitStore) private readonly rateLimit: InMemoryRateLimitStore,
Why it matters: PermissionCache's store sits behind a named DI symbol (PERMISSION_CACHE_STORE) built for exactly this swap. InMemoryRateLimitStore isn't just missing that symbol at the module level — auth.service.ts injects the concrete class directly, confirmed identically in both variants. A Redis swap can't be done by re-providing the module token alone; the injection site itself has to change. Same risk class as the permission cache, strictly worse fix ergonomics.

The one thing that fails open instead of closed

architectural gap — no single file

Deploy 2+ instances with both stores still in-memory and nothing errors. You get inconsistent rate limits and stale permission grants across instances silently — not a crash, not a log line. Every other seam in this codebase (route tiers, ability checks, workspace membership) fails loudly and closed. This is the exception.

Why it matters: the entire design philosophy elsewhere is "an ungated route can't ship silently." A horizontally-scaled deployment running on two stale in-memory caches is the operational equivalent of an ungated route, and nothing names it.

Nothing automatically enforces the one gate that mattersreworded — no CI

registry/combos/*/package.json (4 files, exact grep match) · repo-wide *.yml glob 
{ "test": "vitest run --passWithNoTests" }  // 0 *.test.ts files under registry/combos/**, confirmed in all 4
Why it matters: prove-cycle (145/191 assertions per variant) is the actual correctness gate for backend behavior, and it's rigorous — see above. But pnpm -r test, the obvious "run everything" command, silently passes on every combo with zero real assertions executed. By decision, the fix here is not a hosted CI runner — see Local Enforcement below for the git-hook alternative that respects that constraint.

Combos are hand-duplicated with no drift detector

registry/combos/{nestjs-prisma,nestjs-drizzle}/shared/src/ability.ts

Confirmed directly: nestjs-drizzle's ability.ts is functionally identical to nestjs-prisma's but meaningfully differently worded — each combo is maintained by hand, not generated. The byte-identical rule (registry/README.md) only holds within one combo's two variants, never across the four combos.

Why it matters: a fix to seam logic (say, a CASL edge case) must be manually ported to four codebases with nothing but prove-cycle's assertion count — not its logic — catching drift. Assertion-count-honest is not the same as logic-identical-honest. The fix folds into the same local hook as the enforcement problem above — see next section.

4Recommendations

Enforce prove-cycle locally — no CIP0 · highest impact

Effort: mediumTouches: 8 files — see Local Enforcement for two implementation options
Why
This is still the single highest-leverage fix — that didn't change when CI came off the table. The harness is already rigorous (non-vacuous boot-failure test, front/back CASL equivalence, cross-workspace isolation); it's wasted if nothing runs it before code leaves a machine.
How
A make prove-changed target that diffs against origin/main and runs npm run prove-cycle (both variants) for every touched combo, wired to a pre-push git hook — not a hosted runner. Two ways to wire the hook, compared in Local Enforcement below.
Also fix
The decoy script: delete "test": "vitest run --passWithNoTests" from all 4 combo package.jsons (confirmed present in all 4 by exact grep) so pnpm -r test stops implying coverage that isn't there.

Give the rate limiter the permission cache's swap contractP1

Effort: medium was "small"Touches: 14 files — two different mechanisms
Why
Same failure mode as the permission cache (process-local state, silently wrong once you scale past one instance) — and the fix is bigger than it first looked. Grepping auth.service.ts shows the two NestJS combos inject the concrete class directly, not just wire it through the module — the DI-token fix has to touch the injection site, not only the provider registration.
How — NestJS combos
nestjs-prisma + nestjs-drizzle: add RATE_LIMIT_STORE symbol to shared/src/rate-limit.store.ts (2 files) → register it in variants/{base,workspaces}/src/auth.module.ts (4 files) → change auth.service.ts's injection from the class token to the symbol (4 files). 10 files.
How — Express combos
express-prisma + express-drizzle have no Nest DI — create-auth-app.ts does new InMemoryRateLimitStore() directly. Equivalent fix: accept an optional options.rateLimitStore override in variants/{base,workspaces}/src/create-auth-app.ts. 4 files.
Total
10 (NestJS) + 4 (Express) = 14 files. Reflects the real cost of "no shared runtime adapter" — every cross-combo fix is priced per combo, by design.

Make the horizontal-scale trap fail loud, not silentP1

Effort: smallTouches: 8 files — same composition roots as Rec 2, do both in one pass
Why
This is the one seam in the codebase that fails open by omission, in a codebase whose entire ethos is "fail closed, name yourself." A silent multi-instance deployment on two stale in-memory caches contradicts that ethos more than any code bug would.

Cheapest version: a one-line startup log warning in each of the 8 composition roots (auth.module.ts ×4, create-auth-app.ts ×4) when no explicit store override is given, naming both symbols and what breaks under replication. 5Local Enforcement — no CI

Both designs below run the same two checks — a fast structural drift check and the slow full prove-cycle proof — through git hooks instead of a hosted runner. prove-cycle needs a materialized, migrated, seeded variant against real Postgres, so it can only ever be a pre-push hook regardless of tooling; a structural drift check needs no database and can run at pre-commit, scoped to just the combo files you touched.

Recommended

Zero-dependency .githooks

Native git hooks wired via core.hooksPath, no new dependency.

  • editMakefile — add prove-changed target
  • new.githooks/pre-push — one line: make prove-changed
  • editpackage.json (root) — "prepare": "git config core.hooksPath .githooks"
  • newscripts/check-combo-drift.mjs — structural check, invoked from the same target
4 files · 0 new dependencies · runs automatically on every pnpm install

husky + lint-staged

Conventional tooling; adds a pre-commit fast-path lint-staged gives for free.

  • editpackage.json (root) — devDeps + "prepare": "husky" + lint-staged config
  • new.husky/pre-commit — npx lint-staged
  • new.husky/pre-push — make prove-changed
  • editMakefile — same prove-changed target, reused
  • newscripts/check-combo-drift.mjs — same script, now also wired to lint-staged
5 files · +2 dependencies (husky, lint-staged, plus transitive tree) · pre-commit feedback on staged combo files before you even commit
Call: zero-dependency .githooks, unless the pre-commit-time drift feedback is specifically wanted. This repo carries zero project-wide lint/format tooling anywhere today (confirmed: no root eslint/prettier/biome config — every package handles its own toolchain independently, including the RN app, which is the only one with a real linter). Adding husky+lint-staged would be the first root-level dependency-based tooling layer in the whole repo, for a benefit — catching drift a few seconds earlier than push-time — that's marginal against that cost. Both wire the identical make prove-changed target either way, so nothing about the actual enforcement logic is lost by picking the cheaper option.
Honest limit of either option: a pre-push hook only runs on a machine that has it configured (post pnpm install) and can be skipped with git push --no-verify. It catches "I forgot to run prove-cycle" — the common case — not a deliberate bypass. The same make prove-changed target both designs share is exactly what a CI workflow would call too, if that constraint is ever revisited; nothing here is thrown away by choosing local-only today.
