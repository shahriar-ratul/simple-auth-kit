Every install path was run in a brand-new directory this session

Nothing here is copied from the docs uncritically. Each backend combo was generated into a fresh skeleton with no prior src/lib/auth — simulating exactly what a new consumer does — then installed, migrated against an unmigrated database, seeded, booted, and logged into over real HTTP. Each scaffold app (admin/mobile) was generated into an empty directory, installed, and either production-built or typechecked. Three real gaps surfaced this pass — documented with before/after evidence in Bugs found & fixed — all now fixed in the registry/CLI source, re-verified with a full prove-cycle pass afterward. The CLI's own invocation changed too: it now installs like shadcn/ui — link once, then simple-auth-kit add <combo> from inside any project, and its guided multi-kind flow now shows every available template up front instead of revealing them one prompt at a time.

1Prerequisites

Same as the rest of the repo (see root README.md): Node.js v26+, a package manager (npm works for generated consumer apps — they are plain npm projects, not part of this repo's pnpm workspace), and Postgres reachable at localhost:55432 with a passwordless postgres superuser for anything backend.

# from the repo root
docker run -d --name simple-auth-kit-postgres -p 55432:5432 -e POSTGRES_HOST_AUTH_METHOD=trust postgres:16

# one-time: register the CLI as a global command, shadcn-style
cd cli && npm link

Confirmed working this session: npm link registers simple-auth-kit as a real global binary (a thin launcher, cli/bin/simple-auth-kit.mjs, that spawns the local tsx against simple-auth-kit.ts by absolute path — works regardless of the caller's cwd or global PATH). Don't want to link? Every command below also works unlinked as npx tsx <path-to-repo>/cli/simple-auth-kit.ts add <combo> --into <path>.

2The command shape

# from inside your own project — no --into needed, defaults to cwd
$ simple-auth-kit add <combo> [--workspaces] [--name <AppName>] [--force]
FlagMeaning
<combo>One of the 8 names below — see Backends, Admin, Mobile.
--workspacesInstalls the workspaces variant instead of base (default). Explicit form: --variant workspaces.
--into <path>Only needed if you don't want to cd first — defaults to the current directory. Backend combos merge into it (only src/lib/auth is touched); admin/mobile combos scaffold a whole new app there.
--name <AppName>Scaffold apps only. For mobile-bare-rn this re-templates the native iOS/Android identity (applicationId/bundle id) so multiple generated apps don't collide.
--forceRe-copy over files you haven't hand-edited. Never overwrites a file whose content changed since install (compared against the sha256 manifest in auth.lock.json) — that's reported back as keptModified.

simple-auth-kit init writes a .simple-auth-kit.json so later add runs don't need --path/--alias repeated. Bare simple-auth-kit prints the full combo/flag reference.

3The guided flow — simple-auth-kit add with no combo name

Same shape as shadcn's own no-args add: pick kind(s), then framework per kind, then variant, all via prompts. Selecting more than one kind (e.g. all 3 — API, Admin, Mobile) namespaces each install into its own subdirectory automatically, so a backend + a console + a mobile app can be generated into the same parent directory in one run without colliding.

4Backend combos (merge mode) — 4 combos × 2 variants

Each merges into an existing project's src/lib/auth. All four expose the same AuthModule.forRoot({...}) (Nest) / createAuthApp({...}) (Express) shape and the same route surface once mounted — auth under /auth/*, admin under /auth/admin/*, workspaces variant adds /workspaces/*. They differ in framework glue and in the exact migrate command (Prisma vs Drizzle).

nestjs-prisma verified live — full pipeline

NestJSPrisma
base
simple-auth-kit add nestjs-prisma
workspaces
simple-auth-kit add nestjs-prisma --workspaces

Bring-up (identical for both variants)

  • Set DATABASE_URL and AUTH_JWT_SECRET in .env (openssl rand -base64 32 for the secret)

  • Import AuthModule.forRoot({...}) into your root app module, then npm run start

8Real gaps this verification pass found — all fixed

Prisma and Drizzle config couldn't find the project's .env

Fixed this session

Both prisma.config.ts and drizzle.config.ts started with import "dotenv/config", which loads .env relative to the current working directory — not relative to the config file. The documented commands are cd src/lib/auth && npx prisma migrate deploy and (cd src/lib/auth && npx drizzle-kit migrate), so cwd is src/lib/auth, and the project's real .env at the root was never loaded — for both ORMs equally (an earlier pass through this doc claimed only Prisma had the problem; that was wrong — isolating the test properly showed Drizzle fails identically):

$ cd src/lib/auth && npx prisma migrate deploy
Error: The datasource.url property is required in your Prisma config file
       when using prisma migrate deploy.

$ cd src/lib/auth && npx drizzle-kit migrate
Error  Please provide required params for Postgres driver:
    [x] url: undefined

Fix applied — all 4 combos' shared/prisma.config.ts / shared/drizzle.config.ts now resolve .env from the config file's own location (via fileURLToPath(import.meta.url), matching this repo's existing convention in its own build scripts) and walk up the directory tree until they find one — deterministic regardless of invocation cwd or install --path:

$ cd src/lib/auth && npx prisma migrate deploy
◇ injected env (7) from ../../../.env
9 migrations found in prisma/migrations
No pending migrations to apply.

$ cd src/lib/auth && npx drizzle-kit migrate
◇ injected env (7) from ../../../.env
[✓] migrations applied successfully!

Re-verified after the fix: all 8 examples re-synced via the CLI, the leftover manual .env workaround files removed from every one of them, migrate re-run against the real (already-migrated) databases using only the root .env — and, because this touches config used inside every combo's own black-box proof, npm run prove-cycle re-run for all 4 combos: 145/191 assertions pass, both variants, all 4 combos, no regression.

@simple-auth-kit/auth-client shipped without its compiled output

Fixed this session

The package's dist/ directory is gitignored (correctly — it's build output). But npm pack/npm publish falls back to git's ignore rules for what to include when a package has no explicit "files" field. That means a real npm pack of this package — exactly what happens the day it's actually published, or what any consumer outside this repo's pnpm workspace needs — silently excluded the entire compiled library:

$ npm pack && tar -tzf simple-auth-kit-auth-client-0.0.0.tgz
package/package.json
package/src/auth-client.ts   # source only
package/test/auth-client.test.ts
# dist/ — completely missing

$ npm run build  # inside a generated admin-nextjs scaffold, dependency installed from that tarball
Error: Module not found: Can't resolve '@simple-auth-kit/auth-client'

This was invisible from inside the monorepo because workspace:* resolves via a direct pnpm symlink to the package folder on disk — dist/ exists there even though git never tracked it, so nothing ever exercised the pack/publish path until now.

Fix applied — packages/auth-client/package.json now declares:

"files": ["dist"]

Re-verified after the fix — same tarball-install path, now succeeds:

$ npm pack && tar -tzf simple-auth-kit-auth-client-0.0.0.tgz
package/dist/index.js
package/dist/index.d.ts
package/dist/auth-client.js
package/dist/types.js
package/package.json

$ npm run build   # admin-nextjs scaffold, real tarball install, no monorepo
✓ Compiled successfully — 23/23 pages prerendered, 0 errors

Confirmed the fix doesn't regress anything already relying on the pnpm-workspace symlink path: pnpm -r typecheck (all combos + all 8 apps/*) and auth-client's own 36-test Vitest suite both still pass clean.

CLI invocation didn't actually match its own shadcn-style promise

Fixed this session

cli/package.json's own description already said npx simple-auth-kit add <combo>, but there was no "bin" field — the only working invocation was cd cli && npx tsx simple-auth-kit.ts add <combo> --into ../target, three steps where shadcn needs one. --into already defaulted to cwd (unused ergonomics), so the fix was adding a real bin entry — a thin launcher (cli/bin/simple-auth-kit.mjs) that spawns the local tsx by absolute path, so it works regardless of the caller's cwd or global PATH:

$ cd cli && npm link
added 1 package in 157ms

$ cd /tmp/some-fresh-project && simple-auth-kit add mobile-expo --name "ShadcnStyleApp"
Generated "ShadcnStyleApp" (mobile-expo, base variant) into /private/tmp/some-fresh-project

True npx simple-auth-kit@latest (fetching from the public npm registry, no local checkout at all) still needs an actual npm publish — a separate, deliberately-unmade decision per plan/brief.md for the runtime package, not revisited here. What's fixed is everything reachable without that: one link, then the exact same command shape from any directory. The guided multi-kind flow's template-preview fix is documented separately in §3.
